## 三、分阶段 IOPS 统计口径根因与真值

- **缺陷根因**：`tools/thesis_validation/tv_stats_collector.h` 在进度快照（按 1% 采样）中将 `interval_total_ops`（对于 300k ops 恒等于固定批次大小 3,000 ops）赋给了 `instantaneous_iops`，未除以 $\Delta t$。
- **真值重算**：通过真实时间差 $\text{True IOPS} = \frac{100,000\text{ ops}}{\Delta t}$ 重算分阶段真实吞吐：
  - **T=0**：Phase A **$7,318.8\text{ IOPS}$** $\to$ Phase B **$5,660.3\text{ IOPS}$** $\to$ Phase C（墓碑完全滞留内存）**$3,117.9\text{ IOPS}$**（吞吐崩塌至 3.1k）。
  - **T=256**：Phase A **$48,313.5\text{ IOPS}$** $\to$ Phase B **$63,627.8\text{ IOPS}$** $\to$ Phase C **$37,016.6\text{ IOPS}$**。
  - **T=2048**：Phase A **$35,763.2\text{ IOPS}$** $\to$ Phase B **$51,249.3\text{ IOPS}$** $\to$ Phase C **$33,819.2\text{ IOPS}$**。

## 四、LS24 与小规模 B2 对比：覆盖率稀释定量审计

实测数据表明：**定性退化规律一致，但定量退化幅度因覆盖率被稀释而显著减弱**。
- **覆盖率稀释 20.4 倍**：B2 在 500k Key 空间中 20,000 个删除覆盖了 **~40.0%** 的空间，每次 Scan 大概率命中多个墓碑，Scan 开销达 **210.68 μs/key**；LS24 在 1 亿 Key 空间中保持相同 20,000 个删除使覆盖率降至 **1.965%**，平均 Scan 开销降至 **25.98 μs/key**（退化绝对值减弱 8.1 倍）。
- **点查深度加剧**：在 24GiB 规模下，一旦点查命中删除键，下探底层深层 SST 导致 Get(Del) P99 进一步恶化至 **12.86 ms**。

## 五、后续严谨大规模验证升级路线（规范化协议）

### 1. LS24-Clean（无删除基准对照，3 次重复）
- **数据规模**：100,663,296 Keys (24GiB Payload)，固定 256B Value；
- **负载协议**：严格保持 Get/Scan/Put 轨迹和调度时刻不变，将 DeleteRange 事件替换为调度器 **No-op**；
- **评估指标**：**只比较 Get/Scan 延迟与单位有效 Key 扫描开销（μs/key）**，严禁直接比较包含 No-op 的总 IOPS（避免 No-op 虚高总吞吐）；
- **核心目标**：测定 24GiB 纯净系统下的真实读性能基线，严谨量化 RangeDelete 带来的绝对退化。

### 2. LS24-DensityPreserved（密度与重合度守恒对照，各 3 次重复）
- **数学设计**：在 1 亿 Key 空间（$100,663,296$）中保持 20,000 个 DeleteRange，单次删除跨度设定为 **约 2,000 Key**（理论跨度总和约 4,000 万 Key，实际并集覆盖率控制在 **~35% - 40%**），消除稀释效应；
- **前置准入准则**：**正式运行前必须先执行预检脚本，计算并输出**：
  1. 删除并集覆盖率（Union Coverage Ratio）；
  2. 墓碑重叠率（Overlap Ratio）；
  3. 查询热点重合率（Query Hotspot Overlap Ratio）。
- **对照组**：比较 $T=0$、读优先 $T=256$、写优先 $T=2048$。
