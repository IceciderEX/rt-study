## 二、三层论断体系

### 1. 可确认事实 (Confirmed Facts)

1. **小 Value 场景下 MemTable 自然 Flush 完全缺失**：
   - 在 64B、256B、1024B、4096B 的 Default 组中，前台 Put 写入总物理体积（0.64MB ~ 40.96MB）均未达到 64MB 的 `write_buffer_size` 阈值，导致 Flush 次数均为 **0**；
   - 20,000 个动态范围删除墓碑全部停留在活跃 MemTable 中，读吞吐均被压制在 ~1,700 IOPS，Scan 单位开销在 223~246 μs/key，点查 P95 达 26.7~27.4 ms。
2. **原生固定阈值 `T=256` 在所有 Value 大小下均产生巨大的读恢复收益**：
   - 开启 `T=256` 后，Flush 次数稳定为 **78 次**（全部由 `kMemTableMaxRangeDeletions` 触发）；
   - 64B 下 Scan 单位开销从 227.5 降至 **4.14 μs/key (-98.2%)**，已删点查 P95 从 26.8ms 降至 **145.0 μs (-99.5%)**；
   - 4096B 下 Scan 开销从 246.4 降至 **11.85 μs/key (-95.2%)**，已删点查 P95 降至 **67.3 μs (-99.8%)**；
   - 后台 Compaction 均物理丢弃了 **49.2 万 ~ 49.5 万个过期 Key**，SST 体积发生断崖式缩减（64B: 37MB $\rightarrow$ 0.3MB; 4KiB: 1986MB $\rightarrow$ 47MB）。
3. **写放大与 Value 大小呈现强烈的反比失配关系**：
   - 在 64B 下，固定阈值 `T=256` 产生的写放大高达 **$122.5 \pm 9.9$**；
   - 随着 Value 增大，写放大从 64B 的 122.5 快速下降至 256B 的 104.2、1KiB 的 43.5，并在 4KiB 时降至 **17.5**；
   - 同时，频繁 Flush 引入了前台写入阻塞，导致 Put P99 出现明显毛刺（64B 从 396.6 升至 1,155.6 μs，256B 升至 3,384.4 μs）。

---

### 2. 合理但仍需验证的解释 (Plausible Interpretations)

1. **为什么小 Value 下写放大极高？**
   - 当 Value 很小时，每次因墓碑数量达到 256 而 Flush 生成的 SST 文件体积很小（<1MB），但由于 L0 Compaction 触发阈值为 4，多路合并时会将底层较大的 SST 读入并重新写出。由于前台逻辑写入量（分母）很小，使得写放大（WA = Compaction写入字节 / 前台逻辑Put字节）被极度放大。
2. **为什么 4096B 下 Scan 绝对开销略高于 64B？**
   - 4096B 单键体积大，Block 缓存中容纳的键数量较少，迭代器在底层 SST 中遍历多块物理 Block 时带来的解压与解析开销高于小键。

---

### 3. 当前实验不能推出的结论 (Unsupported Conclusions)

1. **不能得出“T=256 是所有场景下的最优阈值”**：虽然读延迟大幅下降，但在 64B/256B 下带来了超过 100 倍的写放大和前台 Put 尾延迟恶化。
2. **不能将延迟改善完全归因于某一个具体函数**：实验度量的是活跃 MemTable 墓碑下推至 SST 并在后续触发 Compaction 的整体系统效应。
