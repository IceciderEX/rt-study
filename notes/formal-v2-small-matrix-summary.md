## 4. 三层结论陈述

### 4.1 可确认事实 (Confirmed Empirical Facts)
1. **默认 `T0` 在读恢复期（Phase C）发生严重性能崩塌**：由于 $T=0$ 关闭墓碑阈值 Flush，前台 30 万次操作期间无任何 Flush 发生；所有 20,000 条 DeleteRange 墓碑持续滞留在活跃 MemTable 中。Phase C 的真实 IOPS 跌落至 8,556.16，单位有效 Key 扫描耗时恶化至 12.26 $\mu$s/key，Get(Deleted) P99 高达 6.27 ms。
2. **`T256` 显著降低读路径延迟并提升吞吐**：与 `T0` 相比，`T256` 使 Phase C 真实 IOPS 从 8,556 提升至 106,270（提升 12.4 倍），Scan P99 延迟从 6.37 ms 降至 0.47 ms（下降 92.5%），Get(Deleted) P99 从 6.24 ms 降至 0.14 ms（下降 97.7%）。
3. **更激进的阈值（`T64`）伴随显著的写放大与长尾写入延迟**：`T64` 的 Put P99 达到 11.80 ms（相比 `T0` 的 0.18 ms 显著劣化），前台归一化写放大 `pwa_val_norm_fg` 达 48.86；而 `T2048` 的 Put P99 保持在 0.17 ms，写放大仅为 5.82。

### 4.2 合理机制解释 (Sound Mechanistic Explanations)
1. **墓碑滞留机制**：在 LSM-Tree 中，MemTable 采用 SkipList 组织，DeleteRange 存储为独立范围墓碑。在迭代器遍历或点查时，每次 Seek 都需与活跃 MemTable 的 RangeDelAggregator 进行区间重叠判定与版本对比。当未达到容量限制（64MB）时，大量墓碑滞留在活跃 MemTable 中，造成读路径开销随墓碑累积线性增长。
2. **阈值 Flush 与写停顿权衡**：设定固定阈值（如 $T=64, 256$）能及时将墓碑下刷至 SST，从而恢复 MemTable 干净度；但提前切断 MemTable 会导致小 SST 频繁生成，触发 L0 文件的连续 Compaction，从而在上层写入爆发时引发短暂的 Write Stall（使 Put P99 升高）。

### 4.3 当前不能推出的结论 (Non-Extrapolatable Bounds)
1. **不能得出 `T256` 是所有负载的全局最优参数**：本实验基于 500k Keys、256B Value、40% 覆盖率与 8 Worker 分区；在不同数据规模、写批大小与硬件 I/O 带宽下，最优阈值区间可能发生迁移。
2. **不能将 Clean 组总 IOPS 与 Delete 组做等价吞吐比较**：Clean 组将 DeleteRange 替换为 No-op，不产生 WAL 与引擎内部版本链开销，仅作为读性能理论上限参考。
