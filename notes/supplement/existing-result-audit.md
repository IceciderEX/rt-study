## 2. 专项审计问题核验与分析

### 2.1 P1 中 0% 基线吞吐标准差达 ~115k ops/s 的根因核验
- **原始数据**：
  - `rep1`: 耗时 1.00067s $\rightarrow$ 吞吐 **199,865 ops/s**
  - `rep2`: 耗时 0.50045s $\rightarrow$ 吞吐 **399,638 ops/s**
  - `rep3`: 耗时 0.50055s $\rightarrow$ 吞吐 **399,561 ops/s**
- **机制解释**：
  基线工况下完全没有 DeleteRange（纯内存快速点查/扫描），200,000 Ops 在 8 线程下总计算时间仅约 0.5 秒。在 `rep1` 首次运行时，包含线程池建立、C++ 内存分配器预热与计时器首秒截断效应，导致墙上耗时记录为 1.000s，而在后续预热充分的 `rep2/rep3` 中仅需 0.500s。由于总请求数仅 20 万，分母（0.5s vs 1.0s）的亚秒级微小差异直接导致算术计算的 IOPS 在 20 万与 40 万之间跳跃，从而产生了 **115.3k ops/s 的统计标准差**。

### 2.2 每组真实操作组成与比例核验
- **P1 (敏感性)**：Put = 9,997 (5.0%), Scan = 39,950 ~ 40,048 (20.0%), DeleteRange = 0 ~ 19,873 (0% ~ 10.0%), Get = 130k ~ 150k (65% ~ 75%)。
- **P2 (墓碑形态)**：Put = 9,828 (5.0%), Scan = 39,808 (20.0%), DeleteRange = 3,966 (2.0%), Get = 146,398 (73.0%)。
- **P3 Point-Heavy**：Put = 19,983 (10.0%), Scan = 9,985 (5.0%), DeleteRange = 20,153 (10.0%), Get = 149,879 (75.0%)。
- **P3 Scan-Heavy**：Put = 19,983 (10.0%), Scan = 140,016 (70.0%), DeleteRange = 20,153 (10.0%), Get = 19,848 (10.0%)。
- **P4 (局部性)**：Put = 10,071 (5.0%), Scan = 39,940 (20.0%), DeleteRange = 4,005 (2.0%), Get = 145,984 (73.0%)。
- **P5 (回收干扰)**：Put = 10,026 (5.0%), Scan = 40,007 (20.0%), DeleteRange = 4,019 (2.0%), Get = 145,948 (73.0%)。

### 2.3 P2 墓碑形态实验的可比性缺陷（直接促成 S2 设计）
- **核验数据**：
  - `Short-Fragmented` / `Short-Overlapped`：墓碑调用 3,966 次，单段长 50，**并集覆盖率仅 31.25% (156,274 Keys)**；
  - `Long-Contiguous` / `Long-Overlapped`：墓碑调用 3,966 次，单段长 1000，**并集覆盖率高达 80.00% (399,982 Keys)**。
- **问题定位**：原 P2 实验固定了 DeleteRange 调用次数，但未对总删除键空间并集 $U$ 进行归一化，导致长范围组的读性能退化包含了“墓碑覆盖面积更大”的干扰因素。这直接证明了**补充 S2 实验（固定 40% 并集覆盖，仅改变切分粒度）的必要性**。

### 2.4 P4 各组三类 Get 实际采样数与倾斜度核验
- **Cold 组**：`get_affected_live` = 3,468 (2.4%), `get_deleted` = 9,951 (6.8%), `get_control` = 132,564 (**90.8%**)。
- **Medium 组**：`get_affected_live` = 852 (0.6%), `get_deleted` = 10,470 (7.2%), `get_control` = 134,662 (**92.2%**)。
- **Hot 组**：`get_affected_live` = 63,366 (**43.4%**), `get_deleted` = 59,657 (**40.9%**), `get_control` = 22,960 (**15.7%**)。
- **结论**：在热点删除（Hot Zone）下，高达 84.3% 的 Get 请求密集冲击在墓碑及其边界受损区域，直接放大了 P99 延迟。

### 2.5 P5 时间序列采样的缺失（直接促成 S3 设计）
- **核验现状**：原 P5 仅在运行结束时统计了累计 Compaction 丢弃键数与整体吞吐，未能输出按 1 秒采样的动态 P99 波动曲线与 WriteStall 增量，因而无法严谨回答“Compaction 期间是否存在前台性能塌陷”。这直接证明了**补充 S3 实验（1 秒级时间序列采样）的必要性**。

### 2.6 内存与缓存驻留状态确认（直接促成 S1 规模扩展）
- **核验现状**：P1 ~ P5 采用 500,000 Keys × 256B $\approx$ **128 MB** 逻辑数据量。配置的 BlockCache 大小为 128 MB，且宿主机物理内存充足（78GB）。
- **确认事实**：在 P1 ~ P5 中，全部 SST 数据几乎均可被 BlockCache 与 OS 页缓存容纳，缺乏真实的底层 NVMe 物理 I/O 缺页压力。
- **校正决策**：后续 S1/S2/S3 实验将数据规模扩大至 **1,000,000 Keys × 1KiB $\approx$ 1.0 GiB**，保持 128MB BlockCache，使工作集显著大于缓存（8:1），以严谨模拟真实的生产磁盘环境。
