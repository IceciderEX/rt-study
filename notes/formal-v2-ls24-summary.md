## 3. 大规模核心问题直接解答

### 问题 1：默认 `T0` 在真实 24GiB 规模、约 40% 覆盖压力下是否仍存在明显读路径退化？
- **确凿存在极大幅度的读路径退化**：
  1. **单位 Key 扫描延迟**：从 Clean 组的 $1.59\ \mu\text{s/key}$ 恶化至 $21.62\ \mu\text{s/key}$（**13.6 倍退化**）；
  2. **Scan P99 延迟**：从 Clean 组的 $0.73\text{ ms}$ 飙升至 $12.43\text{ ms}$（**17.0 倍退化**）；
  3. **Get(Deleted) P99 延迟**：达到 $12.28\text{ ms}$；
  4. **前台总吞吐**：从 Clean 组的 $14.2\text{ 万 IOPS}$ 骤跌至 $5,918\text{ IOPS}$（**暴跌 95.8%**）。

### 问题 2：`T256` 能否显著恢复 Get/Scan，但是否伴随 Put P99 与引擎输出字节开销？
- **读端大幅恢复，但确实伴随写端停顿与写放大开销**：
  1. **读端恢复**：Get(Deleted) P99 从 $12.28\text{ ms}$ 骤降至 $174.00\ \mu\text{s}$（**下降 98.6%**）；
  2. **写端代价**：触发 76 次 Flush，前台 Compaction 写入达到 $1,206\text{ MB}$，引发严重的 L0 Write Stall，导致 Put P99 飙升至 $9,578.55\ \mu\text{s}$（最高达 $23.51\text{ ms}$）。

### 问题 3：为什么 `T512` 是 24GiB 规模下最强的静态平衡基线？
- **在所有静态阈值中获得最高吞吐与最佳权衡**：
  1. **最高综合吞吐**：Trace IOPS 达到 **$55,121 \pm 12,042\text{ IOPS}$**，大幅超越 T0（$5,918$）、T256（$29,905$）和 T2048（$34,832$）；
  2. **优异的读端恢复**：Get(Deleted) P99 为 $239.29\ \mu\text{s}$（相比 T0 恢复 98.1%），单位扫描耗时降至 $3.19\ \mu\text{s/key}$（全组最低）；
  3. **有效避免写停顿**：Flush 次数稳定为 38 次（比 T256 减少 50%），Put P99 中位数为 $221.18\ \mu\text{s}$（均值 $400.93\ \mu\text{s}$），彻底避免了 T256 出现的 10ms ~ 23ms 级严重写停顿；
  4. **前台写放大显著降低**：前台阶段引擎输出写放大从 T256 的 $55.87$ 锐降至 **$14.45$**（降幅 74.1%）。

### 问题 4：`T2048` 是否进一步降低写端代价，但产生明显的读延迟折中？
- **写端更平稳，但读恢复明显受限**：
  1. **写端平稳**：Flush 仅 9 次，Put P99 为 $217.35\ \mu\text{s}$；
  2. **读端折中**：Get(Deleted) P99 为 $1,222.55\ \mu\text{s}$（**1.22 ms，为 T512 的 5.1 倍**）；SST 磁盘占用增加约 659 MB。

## 4. 三层结论陈述

### 4.1 可确认事实 (Confirmed Empirical Facts)
1. **默认 `T0` 性能严重退化**：在 24GiB 规模下，`T0` 的 Scan P99 达到 12.43 ms，Get(Deleted) P99 达到 12.28 ms，吞吐仅 5,918 IOPS；
2. **`T256` 极致恢复点查但引发写停顿**：Get(Deleted) P99 压制至 0.17 ms，但 Put P99 上升至 9.58 ms（Write Stall 明显）；
3. **`T512` 展现出最优静态综合收益**：综合 IOPS 达 55,121，Get(Deleted) P99 达 0.24 ms，Put P99 中位数仅 0.22 ms，前台写放大仅 14.45；
4. **`T2048` 保持写平稳但读延迟牺牲明显**：Put P99 仅 0.22 ms，但 Get(Deleted) P99 停留在 1.22 ms。

### 4.2 合理机制解释 (Sound Mechanistic Explanations)
1. **墓碑驻留引发内存层求交开销**：活跃 MemTable 容纳的 19,856 条墓碑使每次遍历和点查在 MemTable 层的 `RangeDelAggregator` 处理开销急剧放大。
2. **Flush 频率与 Compaction 级联**：阈值较小（如 256）会高频切断 MemTable 生成碎片化小 SST，触发 L0 Write Stall；$T=512$ 将 Flush 减半（38次），在维持足够墓碑清理密度的同时避开了 L0 堆积峰值。

### 4.3 当前不能推出的结论 (Non-Extrapolatable Bounds)
1. **不能断言 $T=512$ 在所有动态负载下均为最优解**：$T=512$ 在当前工作负载下表现优异，但在读极端密集或写极端密集的倾斜场景下，静态固定阈值依然无法兼顾自适应要求，未来研究自适应控制机制时必须以 $T=512$ 为坚实对比基线。
2. **不能将 Clean 组总吞吐直接视为写等价基准**：Clean 组通过 No-op 跳过删除，仅用于度量无删除条件下的纯净读性能上限。
