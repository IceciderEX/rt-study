## 3. 失败闸门 Rule 5 深度机制剖析

为何在 Rep02 中，Candidate A 的 `peak_actual_sealed_runs` 会精确触碰 24？

### 3.1 时间线事件追踪 (Rep02 Timeline Analysis)
通过追溯 `m2d1a_r_rep02_b64_h32_timeline.csv`，可以准确定位触碰 24 runs 的瞬态：
1. 在 Phase B 运行至删除操作计数 `delete_ranges_issued = 19007` 时，系统正在后台计算深层 L7 归并（将两个 8,192 墓碑的 L7 Run `[272, 530]` 合并为 16,384 墓碑的 L8 Run `556`，耗时约 45.8 ms）。
2. 在该深层归并计算窗口内（从时间线第 1374 行 `MERGE_START` 到第 1394 行 `MERGE_PUBLISH`），前台 8 个并发 Worker 持续产生删除操作，累计新封印了 **19 个 Level 0 Run**（`run_id=551, 553, 554..571`）。
3. 此时内存中已存在的已封印高层 Run 为：`{L1:1, L2:1, L4:1, L7:2}`。按照 AMTV 目录快照语义，在途归并的两个输入 Run（`run_id=272, 530`）在归并完成发布前**仍属于已发布目录**，必须且仅计入一次；尚未发布的输出 Run（`run_id=556`）不计入目录。
4. 当时间线第 1392 行 `run_id=571` 封印发布瞬间（`monotonic_timestamp_us = 2875288393969`），已发布目录 Run 达到第一个峰值 24：
   $$\text{sealed\_run\_count} = 19 (\text{L0}) + 1 (\text{L1}) + 1 (\text{L2}) + 1 (\text{L4}) + 2 (\text{L7 在途输入仍属目录}) = 24 \text{ runs}$$
   对应墓碑总数：$19 \times 64 + 1 \times 128 + 1 \times 256 + 1 \times 1024 + 2 \times 8192 = 1,216 + 128 + 256 + 1,024 + 16,384 = 19,008$ 条，`open_delta_size = 0`，`snapshot_total_tombstones = 19,008`，目录快照守恒严格成立：$\sum (\text{sealed\_run.tombstones}) + \text{open\_delta\_size} == \text{snapshot\_total\_tombstones}$（$19,008 + 0 \equiv 19,008$）。此时采样到的 API 异步计数 `delete_ranges_issued = 19007`，其在线性化位置上晚于或早于实际快照发布时刻，绝不能作为同一瞬间目录守恒的右侧值。
5. 紧随其后，第 1394 行 L7 归并发布（`[272, 530] -> 556`），Run 数降为 23；第 1397 行新封印 `run_id=573` 时短暂再次触碰 24（`{L0:20, L1:1, L2:1, L4:1, L8:1}`，墓碑 $19,072 = 298 \times 64$，守恒同样成立），随后小层级归并迅速收敛回落至低水位。旧版报告草稿因文字粗略将两时刻混淆并误将正在归并的输入 Run 描述为从目录剔除，现已全面更正。

### 3.2 判定边界分析
- 若规则意图是“峰值不得突破或达到 24”（严格严格不等式 `peak < 24`），则 Rep02 的 24 runs 确实违背了该边界。
- 若规则意图是基于软性警戒线（例如允许包含 24，即 `peak <= 24`，或仅作为防止逼近 $H=32$ 的缓冲判定），由于当前硬上限为 $H=32$，24 runs 距离 $H=32$ 仍有 **8 个槽位的绝对物理安全裕度**，因此在实际运行中**并未发生任何 Fallback**（Fallback 恒为 0）。
- **遵守纪律**: 鉴于用户规则明确写明 `A 的 peak_actual_sealed_runs < 24`，且明确指示未通过时 *“不得自动改参数或进入双车道实现，先报告具体失败闸门”*，本报告不做主观放宽解释，如实报告为 **Rule 5 未通过**。
