# P8：范围墓碑压力下的 Flush 预言机验证总结报告 (notes/p8-flush-oracle/p8-flush-oracle-summary.md)

**实验时间**：2026-08-20  
**实验机器**：`s14.servers.hustpdsl.cn` (80 vCPUs, 78GB RAM)  
**底层存储**：`/dev/nvme0n1p2` (KIOXIA EXCERIA PRO 1.8TB NVMe SSD)  
**RocksDB 版本**：纯净官方 Tag `v11.8.0` (commit `abeebd9630f11bd08c28b7bd43c7bdfc62050654`)  
**数据规模**：500,000 个 Key，固定 256B Value (128 MB 原始数据规模)  
**实验设计**：2.0%、5.0%、10.0% 比例下 `default`（无 Flush）vs `oracle-flush`（在 50% 进度点执行一次原生 Flush），每组 3 次独立重复，**共计 18 轮完整运行**。

> **关键事实**：在 18 轮测试中，前台每次 Flush() 仅向磁盘生成一个约 **1.0 MB** 的 L0 SST 文件（包含活跃 MemTable 中的所有范围墓碑和少量前台 Put）。生成的 L0 文件使 L0 文件数达到触发阈值（4 个），随后被 RocksDB 后台 Compaction 机制自动调度吸收。

> 2. **写操作 (Put)**：前台并发工作线程在执行 Put 时，若恰逢控制线程调用 `Flush()` 进行活跃 MemTable 冻结与不可变切换，Put 出现了一次短暂的微秒/毫秒级保护性等待（2% 组 2.2ms，5% 组 7.7ms，10% 组 15.5ms），切换完成后立即恢复正常。

## 四、Compaction 审计与四大确定性硬证据

### 1. RocksDB Ticker 计数口径审计说明
- **审计事实**：
  - RocksDB Statistics 中的 `COMPACT_READ_BYTES` 仅记录经过 Direct/IO 层的特定读取增量，在存在 PageCache 缓存时并未反映整个 SST 文件的逻辑归并输入量；
  - 查验底层日志（`LOG` 中 `EVENT_LOG_v1` 的 `compaction_started`/`compaction_finished` 事件）证实：L0 中的 4 个 SST 文件（131.9 MB）被完整载入并合并生成 L6 的 2 个新 SST 文件（87.9 MB）。
- **立论原则调整**：
  为避免依赖未完全标定的字节级计数器，**P8 核心论证严格优先建立在以下四大确定性硬证据之上**。

## 五、三层论证体系

### 1. 可确认的事实 (Confirmed Facts)
1. **状态一致性 100% 达成**：同一比例下 `default` 与 `oracle-flush` 的最终逻辑 Key/Value 状态与全库 SHA-256 校验和**100% 逐比特完全一致**；
2. **Flush 成功切断内存墓碑累积链条**：在 50% 进度执行 Flush 后，活跃 MemTable 中的墓碑被持久化为 SST 文件，使后半程的 MemTable 重新从轻量级状态开始累积；
3. **后半程读性能显著改善**：Phase C 的吞吐量提升了 2.67 ~ 4.50 倍，扫描单位开销降低了 56.3% ~ 77.6%。

---

### 2. 可支持但仍需谨慎的解释 (Plausible Interpretations)
1. **活跃 MemTable 墓碑堆积是主要瓶颈**：
   P8 实验有力支持了“活跃 MemTable 中未合并的范围墓碑线性累积是引发读长尾急剧恶化的主要瓶颈”的假设。通过主动 Flush 将其转换为不可变 SST 并被 Compaction 吸收，有效消除了内存中的反复范围重叠判定开销。

---

### 3. 不能由当前数据得出的结论 (Unsupported Conclusions)
1. ❌ **不能声称所有生产系统都应当无脑提前 Flush**（Flush 带来了额外的 SST 文件和后续 Compaction 写入开销，在写密集且无读压力的场景下可能导致写放大上升）；
2. ❌ **不能断言 Flush 解决了范围删除的所有性能问题**（下推至 SST 后仍存在多层范围墓碑重叠判定，10% 组 Phase C 的开销仍高于 0% 基准）；
3. ❌ **不能在未做源码级 profile 前将现象绑定到具体 C++ 实现函数**。
