## 一、Smoke 报告两处计数问题追溯与对账说明

### 1.1 墓碑守恒与 Fallback 触发点严格对账

在前期 Smoke 实验（Task 5521）中，Fallback 瞬间的快照结构如下：
- **2 个 L7 Run**：$2 \times 8,192 = 16,384$ 条墓碑
- **1 个 L3 Run**：$1 \times 512 = 512$ 条墓碑
- **1 个 L2 Run**：$1 \times 256 = 256$ 条墓碑
- **12 个 L0 Run**：$12 \times 64 = 768$ 条墓碑
- **Sealed Run 墓碑合计**：$16,384 + 512 + 256 + 768 = \mathbf{17,920}$ 条。

**Open Delta 与全局序号确认**：
- 当 Sealed Run 达到 16 个且后台归并正被一个 L7 耗时归并占据时，前台线程继续写入墓碑。
- 前台 Open Delta 积累到 63 条时，系统总墓碑数为 $17,920 + 63 = 17,983$ 条。
- 当第 64 条墓碑写入时，Open Delta 达到容量阈值 64，触发 Seal 尝试。
- 此时若封口，Sealed Run 将增为 $16 + 1 = 17$ 个，超过硬上限 `hard_layer_limit = 16`。
- 因此，写入端在将第 64 条墓碑加入 Open Delta 并在判决封口时，**原子触发 Fallback**。
- 触发 Fallback 瞬间，内存中存在 **17,920 条 Sealed 墓碑 + 1 个含 64 条墓碑的待封口 Open Delta**，内存中确切驻留的墓碑总量为 **17,984 条**。
- **触发 Fallback 的全局序号**：由于 Phase A 为 100,000 次只读 GetLive，不含任何 DeleteRange，故该触发点确切对应 **Phase B 的第 17,984 条 DeleteRange**（全局 DeleteRange 序号：17,984）。

### 1.2 为什么此前报告同时出现 17,984、18,496（以及 18,368）

在 AMTV 二叉大小分层归并（Binary Size-Tiered Merge）算法中，Sealed Run 数量遵循基本守恒方程：
$$\text{sealed\_runs} = \text{chunks\_sealed} - \text{merges\_completed}$$

由于 Fallback 的触发条件严格由 $\text{sealed\_runs} = 16$ 叠加第 17 个 Chunk 尝试封口时触发（即 $\text{chunks\_sealed} = \text{merges\_completed} + 17$），因此：
$$\text{tombstones\_at\_fallback} = (\text{merges\_completed} + 17) \times 64$$

各个数字对应的是**在后台归并线程被耗时最长的 L7 归并阻塞期间，前台写入与后台已经完成归并的相对线程交错步长**：
1. **17,984 条**：后台累计完成了 **264 次归并**。$(264 + 17) \times 64 = 281 \times 64 = \mathbf{17,984}$。此时后台刚开始执行 L7 归并不久，前台即涌入 12 个 L0，导致在第 281 个 Chunk 封口时溢出。
2. **18,368 条**（Task 5461/5481）：后台累计完成了 **270 次归并**。$(270 + 17) \times 64 = 287 \times 64 = \mathbf{18,368}$。
3. **18,496 条**（本次 B64-H16 诊断实测）：后台累计完成了 **272 次归并**。$(272 + 17) \times 64 = 289 \times 64 = \mathbf{18,496}$。
   在本次实测中，快照中不仅有 2 个 L7，还有 1 个 L4（1,024）和 1 个 L2（256），Sealed Run 合计为 $16,384 + 1,024 + 256 + 768 = 18,432$ 条。加上 Open Delta 的 64 条，恰好为 $18,432 + 64 = \mathbf{18,496}$ 条。

**结论**：此前文字报告中出现不同口径，是因为在多线程并发场景下，单次运行中后台归并线程在被 L7 阻塞前所完成的归并任务数（264 vs 270 vs 272）因微秒级调度存在随机偏差，但**触发机理在代数上完全守恒，均服从 $(\text{merges\_completed} + 17) \times 64$**。

## 三、理论终态分布与墓碑守恒严格校验

当 Phase B 注入恰好 20,000 条 DeleteRange 时，在没有发生 Fallback 的三组配置中，终态墓碑分布严格满足代数分解：

1. **B64 理论解**：
   $$20,000 = 312 \times 64 + 32$$
   将 312 进制拆解为二进制权重：$312 = 256 + 32 + 16 + 8 = 2^8 + 2^5 + 2^4 + 2^3$。
   - 理论 Sealed Runs：1 个 L8 ($256 \times 64 = 16,384$)、1 个 L5 ($32 \times 64 = 2,048$)、1 个 L4 ($16 \times 64 = 1,024$)、1 个 L3 ($8 \times 64 = 512$)。
   - 理论 Open Delta：32 条。
   - 墓碑求和：$16,384 + 2,048 + 1,024 + 512 + 32 = \mathbf{20,000}$ 条。
   - **实测结果**：`drained_sealed_runs = 4`, `drained_open_delta_len = 32`, `drained_level_hist = "{L3:1, L4:1, L5:1, L8:1}"`。**绝对吻合！**

2. **B128 理论解**：
   $$20,000 = 156 \times 128 + 32$$
   拆解：$156 = 128 + 16 + 8 + 4 = 2^7 + 2^4 + 2^3 + 2^2$。
   - 理论 Sealed Runs：1 个 L7 (16,384)、1 个 L4 (2,048)、1 个 L3 (1,024)、1 个 L2 (512)。
   - 理论 Open Delta：32 条。
   - 墓碑求和：$16,384 + 2,048 + 1,024 + 512 + 32 = \mathbf{20,000}$ 条。
   - **实测结果**：`drained_sealed_runs = 4`, `drained_open_delta_len = 32`, `drained_level_hist = "{L2:1, L3:1, L4:1, L7:1}"`。**绝对吻合！**

3. **B256 理论解**：
   $$20,000 = 78 \times 256 + 32$$
   拆解：$78 = 64 + 8 + 4 + 2 = 2^6 + 2^3 + 2^2 + 2^1$。
   - 理论 Sealed Runs：1 个 L6 (16,384)、1 个 L3 (2,048)、1 个 L2 (1,024)、1 个 L1 (512)。
   - 理论 Open Delta：32 条。
   - 墓碑求和：$16,384 + 2,048 + 1,024 + 512 + 32 = \mathbf{20,000}$ 条。
   - **实测结果**：`drained_sealed_runs = 4`, `drained_open_delta_len = 32`, `drained_level_hist = "{L1:1, L2:1, L3:1, L6:1}"`。**绝对吻合！**

## 五、三项核心裁决与定量评价

### 裁决一：B64 / H32 容量缓冲参数定型裁决

根据前台涌水速率与高层归并耗时的物理关系：
$$\text{Required Capacity} = N_{\text{stable}} + (T_{\text{max\_merge}} \times R_{\text{chunk\_arrival}}) + \text{Margin}$$

- $N_{\text{stable}}$：20,000 墓碑下的稳定基态 Run 数量为 **4**（L8, L5, L4, L3）。
- $T_{\text{max\_merge}}$：实测 L7 $\to$ L8 最大单次归并耗时为 **0.0465 秒**（46.5 ms）。
- $R_{\text{chunk\_arrival}}$：Phase B 峰值 Chunk 到达率为 **377.4 chunks/秒**。
- 涌水积压期新增 Run 数量：$0.0465 \times 377.4 = \mathbf{17.55 \text{ 个 Run}}$。
- 峰值瞬态所需容量：$4 + 17.55 \approx \mathbf{21.6 \text{ 个 Run}}$。
- 实际实测中，`B64-H32` 的峰值探查 Run 数为 **20 个**，恰好被 32 容量完美包容！
- **裁决结论**：
  若保持基础分块 $B=64$，则 `hard_layer_limit = 16` 存在确定性溢出设计缺陷。**将容量上限调整为 $H=32$（或 $H=24$）在理论与实测上均能 100% 稳态吸收涌水，且 GetLive P99 依然保持在 21.96 $\mu s$ 的极高水平（远优于回退时的 9,666 $\mu s$），吞吐量达到 277,048 IOPS。**

### 裁决二：B128 与 B256 的可行性裁决

1. **B128 / H16 表现极其优异**：
   - 基础分块扩大为 128 后，相同 20,000 墓碑下的总 Chunk 数由 312 锐减到 156，Chunk 到达率由 377.4 降至 146.2 chunks/s。
   - 在依然保持 $H=16$ 硬上限的前提下，**完全零 Fallback**，峰值 Run 数仅达到 11，余量充足。
   - 归并任务总数从 308 次降至 152 次（减半），总归并时间由 342 ms 降至 245 ms。
   - 前台 IOPS 高达 **225,117 ops/s**，GetLive P99 为 **22.84 $\mu s$**（与 B64-H32 的 21.96 $\mu s$ 几乎一致）。
   - **裁决结论**：**B128 / H16 是极佳的架构优化备选方案**，兼具低层数、低归并开销和极高读性能。

2. **B256 / H16 明显性能劣化**：
   - 虽然 Run 数量更少（峰值仅 7 个），但单次 Open Delta 的线性探查与写端 Copy-on-Write 开销过大（高达 256 墓碑）。
   - 前台 IOPS 大幅跌至 **77,914 ops/s**（下降 72%），GetLive P99 恶化至 **54.06 $\mu s$**，Put P99 / DeleteRange P99 攀升至 1.1 ~ 1.4 ms。
   - **裁决结论**：**B256 过大，严重拖累写路径性能与读端快速过滤效率，予以否决。**

### 裁决三：M2d.2 双车道（Two-Lane）并发归并必要性裁决

- **如果允许调整配置参数**：
  - 方案 A（采用 `B64 / H32`）或方案 B（采用 `B128 / H16`）在现有的**单任务串行归并引擎**下，均已实现 **0 Fallback、225k~277k IOPS、P99 < 23 $\mu s$、内存 0 泄露、验证 100% 正确**。
  - 在这两种方案下，单任务串行归并已经足以消化生产级写入涌水，**无需引入多车道并发归并的复杂线程同步与锁竞争风险**。
- **如果严格约束必须保持 $B=64$ 且硬上限必须为 $H=16$**：
  - 此时，因 L7 耗时（46 ms）与前台涌水速率（2.5 ms/chunk）存在天然物理冲突，则**必须实施 M2d.2 双车道归并**（Lane 0 快速归并 L0/L1，Lane 1 深度归并 Ln），以彻底解耦高层阻塞。
