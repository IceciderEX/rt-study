# LS24-Clean：24GiB 无 RangeDelete 独立基准对照总结报告 (notes/ls24-clean-summary.md)

**实验时间**：2026-08-20 23:51  
**实验机器**：`s14.servers.hustpdsl.cn` (80 vCPUs, 78GB RAM)  
**底层介质**：`/dev/nvme0n1p2` (KIOXIA EXCERIA PRO NVMe SSD)  
**RocksDB 版本**：官方 Tag `v11.8.0`（commit `abeebd9630f11bd08c28b7bd43c7bdfc62050654`）  
**实验设计**：
- **目标**：测定 24GiB 规模下纯净无 DeleteRange 系统的读写性能基准，独立量化范围删除引入的绝对退化倍数；
- **配置**：`NUM_KEYS = 100,663,296`（1.006 亿 Key），`VALUE_SIZE = 256 B`，初始逻辑载荷 24.0 GiB（初始 SST 26.3 GB），`T=0`，Block Cache 128MiB，无压缩，8 线程；
- **负载协议**：严格复用 LS24 的 Get/Scan/Put 访问轨迹与调度时刻，将原 20,000 个 DeleteRange 事件替换为调度器 **No-op**；
- **重要口径**：因 DeleteRange 替换为 No-op，Clean 与 Delete 组的总 IOPS 分母不完全等价，**本报告只比较 Get/Scan 延迟与单位有效 Key 扫描开销**，不宣称端到端总 IOPS 提升；
- **重复轮次**：3 次独立生命周期实测（`ls24_clean_t0000_r01 ~ r03`）。

## 三、核心审计结论

1. **绝对基线确立**：在 24GiB 纯净无删除负载下，底层 NVMe 上的 Scan 单位有效 Key 开销实测为 **$1.17\text{ μs/key}$**，点查尾延迟为 **$127.3\text{ μs}$**，前台 Put P99 为 **$44.1\text{ μs}$**。
2. **RangeDelete 绝对退化量化**：
   - 当在 24GiB 系统中注入 20,000 个 DeleteRange 且未触发 Flush（$T=0$）时，扫描单位有效 Key 开销从 $1.17\text{ μs/key}$ 恶化至 $25.98\text{ μs/key}$（**恶化 22.2 倍**）；
   - 点查尾延迟从 $127.3\text{ μs}$ 恶化至 $12,856.1\text{ μs}$（**恶化 101.0 倍**）；
   - 扫描尾延迟从 $0.54\text{ ms}$ 恶化至 $13.14\text{ ms}$（**恶化 24.5 倍**）。
3. **阈值下推恢复幅度**：$T=256$ 能够将 Scan 开销恢复至 $4.29\text{ μs/key}$（较 T=0 降低 83.5%），并将点查尾延迟压低至 $307.3\text{ μs}$（接近 Clean 基线的 $127.3\text{ μs}$），但代价是引入了 1.64ms 的 Put P99 和 135x 的写放大。
