# E9-DIA 动态混合负载下的范围墓碑缓存失效频率审计正式机制矩阵报告

## 0. 实验概述与约束边界

- **测试目标**：在动态混合负载（500,000 操作、24 线程分片 Trace、Phase A/B/C 三阶段）下，对 `T0`（基线）、`Native-T512`（固定阈值触发）与 `RTP-MC-V2-A`（主动协调器）三组配置执行正式机制矩阵审计（各 $N=3$，共 9 轮），量化范围墓碑“缓存失效—视图物化—锁争用”链条在动态前台运行时的真实表现。
- **执行原则与边界**：
  - **未实现任何 AMTV 代码**；
  - **未对 V2-A 进行任何重新调参**，完全使用已有固定配置；
  - **未改变 RocksDB 正常的 Flush / Compaction 调度策略**；
  - 每轮使用全新独立的 DB 目录（严格限定于 `run-db/e9_dynamic_audit/<exp_id>/db` 内部）；
  - 采用预注册的 $3 \times 3$ 拉丁方交错调度顺序（Latin-Square Interleaved Schedule），完全消除热机、热漂移与时序偏差；
  - 动态审计开启时的延迟与吞吐数据均标记为 **Mechanism-Only**，仅用于内部机制归因，不作为正式工程吞吐对比依据。

### 1.3 正确性对账与恒等式硬校验
1. **全库版本感知对账**：
   - 9 轮测试的终态存活键数均为 `316,193`（与理论状态机模型预测 `316,193` 100% 吻合）；
   - 9 轮测试的 RocksDB 全库 SHA-256 均为 `366c5e5b3e5c4e5558be1175b16f5e76b8c71be13bb8e607fae36492d09f1c34`；
   - 对账状态全部为 `>> PASS <<`，无任何丢键或数据损坏。
2. **三级包含排斥恒等式硬校验**：
   - 恒等式：$$\text{affected\_union} \equiv \text{materialized} + \text{lock\_contended} - \text{both}$$
   - 在 Worker 线程级（1,296 样本）、Phase 阶段汇总级（216 样本）、Full Run 全流程汇总级（9 样本）三级均无条件执行断言检查，100% 校验通过；
   - 观察到在单次读 API 细粒度探针中，物化发生的读者是在获取锁后执行物化，而其他受影响者是在等待该锁，单次操作差分中 `both_count = 0`，但汇总与报表严格输出 `both_count` 并遵循容斥公式，不预设两类事件天然互斥。

> [!WARNING]
> **时序准则：不得把异步 Flush 完成时间直接解释为触发阶段**：
> RocksDB 的 MemTable 切换（`SwitchMemtable`）是**同步前台写操作**，当追加第 512 条 DeleteRange 时立即封表并加入不可变队列（Immutable MemTable List），由后台 Flush 线程异步将数据写入 SST。**因此触发阶段由前台写切表时间决定，异步落盘完成时间仅反映刷盘耗时。**

### 5.2 审计事实归因
1. **Phase A 内部确实发生且完成了代际切换与 Flush**：
   - 预加载阶段使用了 Gen 1、2、3；前台启动后，活跃 MemTable 为 **Gen 4**；
   - Phase A 规划写入 1,200 条 DeleteRange。当写入第 512 条 DeleteRange 时（前台时间 **0.2592 s**），Gen 4 严格达到 `memtable_max_range_deletions = 512` 触发切表，并于 **0.3071 s**（Phase A 结束前 52 ms）完成落盘（生成 `000015.sst`）；
   - 随后分配的 **Gen 5** 继续在 Phase A 内接收剩余的 $1,200 - 512 = 688$ 条 DeleteRange，并使墓碑数再次累积到 512，于 Phase A 与 Phase B 交界处触发第二次切表（Job 7）；
   - 在 Gen 4 切换前，读者在活跃 MemTable 中观察到的墓碑数量线性上升至 511 条（第 512 条触发同步切表），**这完全解释了为何 Phase A 记录的最大物化墓碑数为 511**。
2. **此前表格显示“Phase A Flush 为 0”的技术原因**：
   - 此前的 `phases.csv` 输出结构中未包含按阶段切分的 Flush 计数器（仅在全流程汇总 `summary.csv` 中输出了总数 19 次）；
   - 当初撰写简报时，未对各阶段内的离散后台事件进行时间线对齐，导致 Phase A 被粗略填作 0；
   - 本次通过对底层时序进行严格审计，确认 **Phase A 实际触发了 1 次 Flush（并在 Phase A 内完成），Phase B 触发 10 次 Flush，Phase C 触发 7 次 Flush，Cooldown 触发 1 次 Flush，合计准确为 19 次**。

## 七、 核心机制归因与 AMTV 候选方向评估结论

根据 E9 正式机制矩阵（9 轮）的详尽数据，我们确定以下严格的结论边界：

1. **T512 并未降低该 Trace 下的缓存失效/物化发生频率，而是限制了每次物化面对的墓碑规模**：
   - 数据表明，三组配置的每千读物化率几乎相同（全流程均为 $48.0 \sim 48.5$ 次 / 1,000 reads，Phase B 均为 $171.5 \sim 174.9$ 次 / 1,000 reads）；
   - T512 读尾延迟收益的本质，在于通过激进的切表将单次物化面对的活跃 MemTable 墓碑数硬性限制在 $[1, 513]$（均值 251.6），使红黑树单次物化时间极大缩短，进而使锁等待延迟占比从 T0 的 73.23% 压缩至 22.02%。

2. **V2-A 未能有效限制该规模，因此未复制 T512 的读端收益**：
   - V2-A 试图在读敏感时 HOLD、在写突发时 YIELD 以减少写放大，导致其在 Phase B 积累了多达 1,669 条墓碑（均值 533 条）；
   - 这使得 V2-A 的物化与锁争用链条未被切断（锁争用延迟仍占 34.57%，合计占 46.11%），读 P99（815 us）大幅超出 200 us 的读 SLO。V2-A 在该 Trace 下的失败可部分由其未能有效截断“失效—物化—锁等待”链条解释。

3. **AMTV 是有动态证据支持的候选方向，但尚未证明能在相同读 SLO 下减少 Flush、写放大或优于 T512**：
   - 动态矩阵数据为“在读路径上消除同步重建物化和锁竞争”提供了坚实的机制支持：在活跃 MemTable 中维护只读或增量墓碑视图（AMTV）在理论上可以直接规避读者排队；
   - **但是，AMTV 要想证明自身相对于 Native-T512 的工程优势，必须在后续原型开发中证明：其不仅能达成与 T512 相当的读尾延迟 SLO，而且必须在相同读 SLO 下显著减少 Flush 次数（打破 T512 所依赖的 19 次激进切表），且不增加写放大。**
   - **本报告明确禁止使用“唯一根因”、“100% 定位”、“AMTV 必然更优”等非严谨断言。后续结论必须严格依赖 AMTV 原型代码的真实实现与对照测试数据。**
