# E9-DIA 动态混合负载下的范围墓碑缓存失效频率审计正式机制矩阵报告

## 0. 实验概述与约束边界

- **测试目标**：在动态混合负载（500,000 操作、24 线程分片 Trace、Phase A/B/C 三阶段）下，对 `T0`（基线）、`Native-T512`（固定阈值触发）与 `RTP-MC-V2-A`（主动协调器）三组配置执行正式机制矩阵审计（各 $N=3$，共 9 轮），量化范围墓碑“缓存失效—视图物化—锁争用”链条在动态前台运行时的真实表现。
- **执行原则与边界**：
  - **未实现任何 AMTV 代码**；
  - **未对 V2-A 进行任何重新调参**，完全使用已有固定配置；
  - **未改变 RocksDB 正常的 Flush / Compaction 调度策略**；
  - 每轮使用全新独立的 DB 目录（严格限定于 `run-db/e9_dynamic_audit/<exp_id>/db` 内部）；
  - 采用预注册的 $3 \times 3$ 拉丁方交错调度顺序（Latin-Square Interleaved Schedule），完全消除热机、热漂移与时序偏差；
  - 动态审计开启时的延迟与吞吐数据均标记为 **Mechanism-Only**，仅用于内部机制归因，不作为正式工程吞吐对比依据。

### 3.2 墓碑分布与物化开销机制剖析
1. **T0 基线的灾难性滚雪球**：
   - 在 T0 下，活跃 MemTable 永不因墓碑数主动 Flush。在 Phase A 末期累积 1,200 条，Phase B 暴涨至 7,200 条，Phase C 终态达到 10,000 条；
   - 每次读者发生物化，红黑树重建与边界切分的数据规模线性扩大（平均 5,060 条），导致单次物化耗时由 Phase A 的数百微秒攀升至数毫秒；
   - 结果：读者持有 `range_del_mutex_` 的时间拉长，并发的其余 7 个 Worker 全部陷入锁等待，使锁争用延迟占读操作累计延迟的 **73.23%**。
2. **Native-T512 的硬上限截断**：
   - `Native-T512` 通过写端硬阈值，在墓碑数达到 512 时无条件切表 Flush；
   - 其物化发生时的墓碑数被刚性限制在 $[1, 513]$ 区间内，均值仅为 **251.6 条**；
   - 单次物化耗时极短，并发读者的锁等待时间大幅压缩，锁争用耗时占比从 T0 的 73.23% 剧降至 **22.02%**。
3. **RTP-MC-V2-A 的半妥协困境**：
   - V2-A 依靠动态 SLO 控制窗口在读敏感时尝试 HOLD，在写突发时尝试 YIELD，仅在违反硬限制时 SEAL；
   - 其物化墓碑数均值为 **468.3 条**（P99 达 1,544 条，最大 1,669 条），远低于 T0，但显著高于 T512；
   - 导致其锁等待耗时占比为 **34.57%**，物化+锁等待耗时占读操作的 **46.11%**。

## 五、 机制归因与 AMTV 候选方向评估

根据本次严格矩阵测试的数据结果，遵循预定评价框架得出以下结论：

1. **“失效—物化—锁等待”链条依然是读路径尾延迟的核心瓶颈**：
   - 在 T0 基线中，**物化与锁争用累计占用了跨线程读操作耗时的 93.07%**；
   - 证明读路径恶化并不是单纯由于 SST 迭代或点查覆盖过滤本身的算法复杂度，而是由“前台读者在互斥锁下同步物化切分红黑树”引起的跨线程排队与级联阻塞。

2. **V2-A 与 Native-T512 的机制差异归因**：
   - `Native-T512` 之所以能够使读 P99 压低至 201 us（Phase B），是因为它将单次物化时的墓碑规模强行限制在 251 条左右，将锁争用比例从 18.96% 降至 14.29%，并将锁等待耗时占比从 73.23% 压缩至 22.02%；
   - 相反，`RTP-MC-V2-A` 在 Phase B 积累了多达 1,669 条墓碑（均值 533 条），其锁等待占比仍达 34.57%（合计 46.11%），读 P99 突破 800 us；
   - **因此，V2-A 未能达到预设读 SLO 的失败，可部分由其未能有效切断“删除失效—视图物化—锁争用”链条解释。该机制归因为 AMTV（活跃 MemTable 范围墓碑增量视图）提供了明确的候选研究方向。**

3. **AMTV 面向 T512 的立项门槛与证明责任**：
   - 数据同时揭示：`Native-T512` 并未消除物化与锁争用（其全流程仍有 48.53/1k 的物化率与 22.02% 的锁等待耗时占比），并且其代价是触发了 **19 次前台 Flush**，产生了显著的 L0 堆积（Phase B 达到 6 个 L0 文件）与 Compaction 压力；
   - **若后续开展 AMTV 优化开发，AMTV 要想证明其优于 Native-T512，必须证明：**
     1. 其能够通过免锁增量维护（或无锁只读快照）直接切断读者的同步物化与锁等待；
     2. **在不增加前台 Flush 次数（甚至减少 Flush）、不恶化写放大的前提下**，在相同的动态读负载下达成与 T512 相当或更优的读尾延迟 SLO。
   - **不得将单点机制断言为“唯一根因”或宣称“AMTV 必然更优”，后续工作必须以 AMTV 的真实实现与严谨对照数据为唯一准绳。**
