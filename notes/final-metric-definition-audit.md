## 一、指标定义与统计口径统一规范

### 1. 延迟指标 (P50 / P95 / P99 / Mean) 计算口径

| 延迟口径名称 | 统计范围与算法 | 样本量 (Sample Count) | 原始数据来源 | 适用场景与命名规则 |
| :--- | :--- | :--- | :--- | :--- |
| **全量原始样本全局分位数** <br>(`overall_p99_us`) | 在整轮生命周期内，对前台驱动发出的**每一个单次请求**记录纳秒耗时，存入 `TVLatencyTracker`，运行结束时基于全量样本排序计算精确 99 分位数。 | 对应操作总数（如 Put 为 70,000，Scan 为 60,000，Get 为 150,000） | `summary.csv` 中的 `put_p99_us`, `scan_p99_us`, `get_del_p99_us` | **全生命周期总体尾延迟**（主表核心指标） |
| **分阶段聚合分位数** <br>(`phase_p99_us`) | 在特定阶段（如 Phase A: 1%~33% 进度）的所有进度快照中，提取该阶段内各快照点记录的窗口 P99，计算其 95 分位数或均值。 | 33 个进度快照点 | `timeseries_progress.csv` 聚合生成 | **阶段内尾延迟代表值**（分阶段明细表） |
| **逐秒瞬时分位数** <br>(`sec_p99_us`) | 1 秒后台监控线程每秒采集一次过去 1 秒窗口内的所有操作样本，计算该 1 秒内的即时 P99。 | 过去 1 秒内完成的操作数（数千至数万） | `timeseries_wallclock.csv` | **时间序列时变曲线绘制** |

> **口径纪律**：全量原始样本全局 P99 与分阶段快照聚合 P99 在表中必须明确注明列名与来源，禁止相互混用或简单等同。

### 2. 吞吐指标 (Throughput / IOPS) 计算口径

| 吞吐口径名称 | 计算公式 | 分子与分母定义 | 适用场景与约束 |
| :--- | :--- | :--- | :--- |
| **全生命周期总体吞吐** <br>(`overall_iops`) | $\text{IOPS} = \frac{\text{total\_ops}}{\text{total\_elapsed\_sec}}$ | 分子：总前台操作数（如 300,000）<br>分母：前台压测起止总耗时（秒） | **全程吞吐核心指标** |
| **分阶段真实吞吐** <br>(`phase_true_iops`) | $\text{True Phase IOPS} = \frac{\Delta \text{ops}}{\Delta t}$ | 分子：该阶段内完成的操作数（如 100,000）<br>分母：该阶段的实际耗时 $t_{\text{phase\_end}} - t_{\text{phase\_start}}$（秒） | **分阶段真实吞吐指标** |
| **进度批次大小** <br>(`progress_batch_size`) | $\text{Batch Size} = \text{total\_ops} / 100$ | 每 1% 进度的固定操作计数（如 300,000 ops 下恒等于 3,000 ops） | **快照步长计数，严禁作为速率/IOPS使用** |

---

### 3. 写放大 (Write Amplification) 三层口径

| 写放大口径 | 计算公式 | 说明 |
| :--- | :--- | :--- |
| **逻辑写放大 (LWA)** | $\text{LWA} = 1.0$ | 逻辑写入无放大 |
| **Compaction 写放大 (CWA)** | $\text{CWA} = \frac{\text{compaction\_write\_bytes}}{\text{logical\_put\_bytes}}$ | 仅衡量后台 Compaction 引起的额外重写倍数 |
| **总物理写放大 (PWA)** | $\text{PWA} = \frac{\text{flush\_write\_bytes} + \text{compaction\_write\_bytes}}{\text{logical\_put\_bytes}}$ | 衡量从 MemTable 下刷至 SST 及后续 Compaction 的全部存储物理写入放大 |

- **后台代价明确结论**：
  1. 16MiB 组在读端性能恢复（Scan 开销降 73.4%，尾延迟降 75.9%）的同时，**伴随了确凿的后台 Flush 写入代价（13.33 MB 物理 I/O）与 SST 空间增量（+14.33 MB）**；
  2. 64MiB 和 128MiB 组因为 32MB 写入未达到阈值，Flush 与 Compaction 物理写入均为 0 MB；
  3. 在 B1-CF 负载下，由于产生的 L0 文件数仅为 2 个（未达到触发 Compaction 的 4 个阈值），未触发后续 Compaction，因此 Compaction 写入为 0 MB。
  4. **不能声称 16MiB 是“无代价”的**：其读端改善是直接以 13.3MB Flush 物理 I/O 为代价换取的。
